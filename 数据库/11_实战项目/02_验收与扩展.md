# 第 11 章 · 验收与扩展

> 最后一关是证明工具真的能失败，而且失败以后数据仍然干净。

## 学习目标

- 用一次成功写入、两次拒绝写入与边界报表验收。
- 复现 WHERE 误删零记录主题的错误并修复。
- 给新需求写出可运行的验收条件。

## 准备

沿用上一课的项目文件和 `2026-11-20` 成功写入。如果你还没加那条 20 分钟记录，报表中 SQL 应为 2 次 60 分钟而非 3 次 80 分钟。不要重复执行那条新增命令来「校正」结果，用实际记录为准。

## 一、先验证两种失败不会留下记录

```powershell
python .\study_log.py session "不存在" 2026-11-20 20
python .\study_log.py session "SQL" 2026-11-20 0
python .\study_log.py report 2026-11-01 2026-12-01
```

第一条找不到可写主题，第二条触发时长检查。都是失败退出，报表保持之前的时长。如果在 PowerShell 核对退出码，要在每条命令后立即看 `$LASTEXITCODE`，下一个命令会刷新它。脚本的 `with connection` 在块里发生异常时会回滚；外层 `closing` 负责关闭连接。

再归档一个主题，确认新旧行为分别符合要求。每个练习文件只归档一次。

```powershell
python .\study_log.py archive "Python"
python .\study_log.py session "Python" 2026-11-22 15
python .\study_log.py report 2026-11-01 2026-12-01
```

第一条成功，第二条因已归档被拒绝，最后仍能查到旧的 `Python | 1 次 | 30 分钟`。这是归档与物理删除的实际差别。

## 二、在 SQLite 客户端独立复查报表

用 DB Browser for SQLite 打开 `c11_study.sqlite3`，把程序的日期参数换成下面两个固定的日期字面量。这是 SQLite SQL，不在 HeidiSQL 的 MySQL 连接运行。

```sql
SELECT t.name, COUNT(s.id) AS session_count, COALESCE(SUM(s.minutes), 0) AS total_minutes
FROM c11_topics AS t
LEFT JOIN c11_sessions AS s ON s.topic_id = t.id
  AND s.studied_on >= '2026-11-01' AND s.studied_on < '2026-12-01'
GROUP BY t.id, t.name
ORDER BY total_minutes DESC, t.id;
```

应同时看到 SQL、Python 和分析。若把日期条件移到 `WHERE`，分析的补空行无法比较日期，报告少一行。若改用 `COUNT(*)`，分析的补空行会被当成一次记录。你可以有意识地构造退化对照，再恢复正确写法。

## 三、给第二版划出一道清晰的小改动

例如添加「只看活跃主题」报表。先写预期：归档 Python 后，默认历史报表仍有其 30 分钟；显式选择只看活跃主题时，返回 SQL 与分析。改动落在主题侧的筛选，保留 `ON` 内的日期区间。这样不用先改库，也能独立验证需求是否做对。

这里汇总出的分钟数是可随明细重建的。在加缓存、周报导出或新索引之前，先确定用户需要的粒度、快照时间与性能目标，用一次实际查询证实。

## 小结

做完项目的标准是，另一条查询能复算你的报告，非法输入不能写进去，重要边界都能用固定样本复现。
