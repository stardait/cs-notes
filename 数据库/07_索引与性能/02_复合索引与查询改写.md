# 第 07 章 · 复合索引与查询改写

> 复合索引像按两级目录排列。你的条件要说明先去哪一段，再在那一段里找什么。

## 学习目标

- 解释前导列、范围与排序如何配合。
- 用等价的日期边界改写查询，验证常见的回表和成本取舍。

## 准备

缺表时运行[配套 SQL](00_安装配套表.sql)。表 `c7_orders` 有 20,000 行，客户号 1～200，每位各 100 笔。建表时已创建 `(customer_id, created_at)` 索引。造数据的语句仅用于准备样本。
```sql
USE learn;
SELECT COUNT(*) AS orders, COUNT(DISTINCT customer_id) AS customers FROM c7_orders;
```

## 一、先按客户分段，同一个客户内再按时间排

`(customer_id, created_at)` 比较时先看客户，客户相同再按时间。单独指定 `customer_id = 42` 可以定位客户 42 的一段。再加时间范围，可以把这个区间缩窄。若只给日期，时间段横跨多个客户，不形成一个连续的客户区间。优化器仍可能扫描某个索引或使用其他优化，实际要看计划。

```sql
SHOW INDEX FROM c7_orders;

EXPLAIN FORMAT=TRADITIONAL
SELECT id, amount FROM c7_orders
WHERE customer_id = 42
ORDER BY created_at DESC LIMIT 3;

EXPLAIN FORMAT=TRADITIONAL
SELECT id, amount FROM c7_orders
WHERE created_at >= '2026-01-02' AND created_at < '2026-01-03';
```

第一个查询在一个客户内部取最近三笔，可以逆向访问对应索引。第二个查询要覆盖所有客户。若主要业务经常全店按日查询，考虑以 `created_at` 为首列的索引，再对照计划和写入成本。仅凭一个查询的结果决定索引数量，很容易给其他查询和写入增加负担。

## 二、固定条件，比较两种日期写法

```sql
SELECT COUNT(*) AS matched FROM c7_orders
WHERE customer_id = 42 AND DATE(created_at) = '2026-01-02';

EXPLAIN ANALYZE
SELECT id, created_at, amount FROM c7_orders
WHERE customer_id = 42 AND DATE(created_at) = '2026-01-02';

EXPLAIN ANALYZE
SELECT id, created_at, amount FROM c7_orders
WHERE customer_id = 42
  AND created_at >= '2026-01-02' AND created_at < '2026-01-03';
```

两种条件对应同一天，结果都是 8 行。第一种仍可用索引找客户 42，但普通索引存的是 `created_at` 原值。这个样本中，引擎对该客户约 100 笔记录做额外日期判断。第二种直接为时间列给出连续范围。用 `DATETIME` 时这里比较当地业务日期字面量；业务若按用户时区统计，先把起止时刻统一到存储口径。

## 三、为一条真实查询设计索引

InnoDB 的二级索引条目带有主键。已有索引能从索引记录里得到客户、时间和 `id`；若还要 `amount`，通常要用主键再查表记录。只选必要列，有机会避免这一步。不要为了让所有查询都能只读索引而把每一列加进去，存储和每次写入都要维护这些索引。

试着在会话临时表里创建并移除一个索引，避免碰课程样本。

```sql
CREATE TEMPORARY TABLE c7_index_lab (
    id INT PRIMARY KEY,
    occurred_at DATETIME NOT NULL
) ENGINE=InnoDB;
CREATE INDEX idx_c7_lab_time ON c7_index_lab (occurred_at);
SHOW INDEX FROM c7_index_lab;
DROP TEMPORARY TABLE c7_index_lab;
```

计划里应看到索引元数据。真正增加索引时要考虑构建过程和维护成本。先写业务最常执行的过滤、排序、返回列，再验证执行计划与收益。

## 小结

先让条件针对索引能区分的原值，再考虑复合索引列顺序。定索引时同时看读取、写入和维护成本。

## 动手练习

### 练习 1 · 取客户 42 最新三笔

用时间降序取客户 42 最后 3 单，确认结果排序。

<details>
<summary>展开参考答案</summary>

```sql
SELECT id, created_at FROM c7_orders
WHERE customer_id = 42
ORDER BY created_at DESC LIMIT 3;
```

19842、19642、19442。该客户的订单时间没有并列；如果业务可能同一时刻插入多单，应再用唯一键打破并列。

### 练习 2 · 状态列单独做索引吗

约三分之二订单是 paid。只查全部已付款订单时，为 status 建索引就一定更快吗？

<details>
<summary>展开参考答案</summary>

不一定。命中比例高且要许多列时，索引访问可能需要大量查表。先用 EXPLAIN 看估算，使用恰当规模的数据比较真实读量，再决定。

</details>
